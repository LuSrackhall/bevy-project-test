## 03:37 · workbuddy · 调研 agent 记忆方案：文件派与向量派的适用边界

- **调研**（外部资料，本仓无代码改动）：
  - 社区并非铁板一块：Claude Code、Cursor、Windsurf 的官方记忆都是 markdown/本地文件；OpenClaw 走 SQLite + FTS5 + sqlite-vec 折中；Mem0、Zep/Graphiti 一类走向量 + 时序图。
  - 文件派的三条硬理由：① 零 false negative —— 读进 context 就一定生效，而向量检索受相似度阈值影响会**静默漏掉**记忆；② 可审计可修正 —— 改一行再 `git diff`，而向量库要经 API 找到对应 embedding 删除重插；③ 语义工作在写入时做一次，而非每次查询都付。
  - 文件派公开的失败模式：主流实现（Claude Code、Cline、Cursor、Windsurf）**均不处理并发写**；无语义排序；索引摘要过时会漏文件；规模天花板约在"单 agent/团队 5000 条记忆以内"。
  - 可偷的模式：`MEMORY.md` 退化为**索引**（一行一个文件），细节拆到主题文件按需加载，避免常驻文件无限膨胀。
- **对照本仓现状**：
  - 三层结构恰好对应社区总结的记忆分类：`AGENTS.md` + `.agents/skills/` = procedural、`MEMORY.md` = semantic、当日日志 = episodic。社区首要忠告是"三类不要混在一个 store"，此处天然分离。
  - 上文 03:03 条目遗留的"多会话同写当日日志"冲突风险，与社区公认的文件派失败模式**同源**，非本仓特有问题；若真出现冲突，按 agent 拆文件是已知解法。
  - 本仓相对社区同类方案的稀缺点：**记忆纳入 git** —— 可 diff / review / revert / 随代码进 PR。Claude Code 等的记忆默认不受版本控制，这一点是少数派做法。
- **遗留**：以下三项为候选改进，**尚未写入 `AGENTS.md`**，待用户确认后再动手 —— ① `MEMORY.md` 改为索引结构；② 明确 episodic / semantic / procedural 三类记忆各自的写入策略；③ 补规模判据与并发写的缓解手段。
